## Cleanup
Design debts found reviewing the code (2026-10-11), most important first. None changes what the IDE does.
1. ~~**`App` does too much**~~ Done: `ide/app.py` is ~930 lines (56 methods), keeping the window, menus, documents, Edit, Find, F1 help and completion; its jobs are parts of it (`ide/part.py`), each in its own module: `app.runner` (`running.py`), `app.debug` (`debugcontrol.py`), `app.files` (`projectfiles.py`), `app.envs` (`environments.py`).
2. ~~**Editors have no shared interface**~~ Done: a base `Editor` in `ide/editors.py` says what each is (`read_only`, `plain`, `has_design`, `is_project_code`, `showing_design()`).
3. ~~**Breakpoint and watch state is spread out**~~ Done: `ide/breakpoints.py` keeps them (storing, reading open and closed files', changing, renaming); `app.debug` shows them and tells the program.
4. ~~**The IDE–program messages are unwritten**~~ Done: `readymade/protocol.py` names every command, event and pause reason (`Cmd`, `Event`, `Reason`) with each one's fields; both sides send through `protocol.check()`, and `tests/test_protocol.py` checks every send in the code against it.
5. ~~**Private parts used across classes**~~ Done: what's used elsewhere is public (`one_step`, `show_above_code`, `idle`, `pip_install`, `fill_folder`, `check_new_name`, `layout.span`); the form and designer use functions in `controls` (`grid_of`, `focus_widget`, `option_group`, `show_as_default`), as a control's public methods are what programs see; a Canvas's shapes are a `ShapeSet` in `shapes.py`; `form.loaded_forms()` and `form.track_task()`.
6. ~~**The project's files are listed seven ways**~~ Done: `Project.files()` lists them all (forms, modules, then the other files folder by folder, skipping hidden folders, caches and build output), with `python_files()` for the code and `snapshot()` built on it; Search & Replace, Rename Module and the list of a form's uses use them, and `app.files.text_of()` reads an open tab's text before the disk's.
7. ~~**Names are checked five ways**~~ Done: `readymade/names.py` has `check_python_name`, `check_module_name` (no hiding Python's own modules) and `check_file_name` (Windows' rules, the strictest); controls, menus, forms, modules, programs and files all use them, and `Project.name_taken()` checks forms and modules in any case.
8. ~~**Every dialog builds its own buttons**~~ Done: `ide/dialog.py`'s `Dialog` gives a body and a row of Help / OK / Cancel with Enter, Esc and F1; Add Watch, Quick Watch, Breakpoint, Options, Make EXE, Linting/Formatting, the Menu Editor, Create Environment and the Properties list editor use it.
9. ~~**Big but not urgent**~~ Done: `readymade/controls/` is a package (`base.py`, `traits.py`, and the 12 controls by family); the traits are public (`BackColor`, `TabStop`, `WidgetText`...), and the form and designer ask what a control can do (`can_be_default`, `access_key_action`, `arranges_inside`) instead of its type. The IDE's menu bar and shortcuts are one table, `ide/menubar.py`: each command is written once with its key and when it can be used, and `tests/test_menubar.py` checks no key does two things on any system. Still to decide, with third-party controls: how the IDE loads a library's controls from the project's environment.

## Code editor
- **Options follow-ups**: more themes; mark a run-time error's line in the line numbers; let a project ask for an indent width (today it's each person's, and generated handlers always use 4). Dark gaps: the menu bar on Windows and macOS (the system draws it), dialogs' title bars on Windows (only the main window's is dark), and the font chooser's family list.
- **A modern look**: the Sun Valley ttk theme (`sv-ttk`, MIT, pip-installable) gives ttk widgets a Windows 11 look in light and dark. It could go in the `ide` extra, used when installed and falling back to today's clam-based look. Tabs, buttons, fields, scrollbars and lists would change; the Toolbox buttons (plain Tk), the code area and the menus keep their own colors, and Windows still draws its menu bar white (darkening it needs undocumented Windows calls).
- **Folding** and an outline, from an error-tolerant parser (parso, MIT). The same parsing would let Enter see past the current line: today, after a call spread over several lines, the next line keeps the continuation indent instead of returning to the statement's level.
- **A language server option (LSP)**: completion and definitions use Jedi today. An LSP client would let people choose Pyright (or basedpyright, which pip-installs with its own Node.js), python-lsp-server, jedi-language-server or Ruff's server, configured like linting, and would also bring hover info, signature help and rename. Pylance can't be used outside Microsoft's VS Code. The form-control declarations (assist.py) carry over, as the IDE chooses the text it sends.
- **Completion follow-ups**: `forms.<name>` (forms are found by name at run time), signatures and docstrings beside the list, Back after Go to Definition (Alt+Left).
- **Help follow-ups**: show help beside the completion list for the chosen entry; help on hover; links between topics (a property's help linking to its control); format reStructuredText and Google-style docstrings instead of showing them as plain text.
  - Color codes get stripped out via PYTHON_COLORS or NO_COLOR because that broke the "jump to error line" feature.  Is there ever a situation where colors in help could be useful?
- **Formatting follow-ups**: format just the selection; let a project insist on no formatting (today an unset project falls back to each person's default); format in the background instead of briefly waiting with a busy cursor.
- **Linting follow-ups**: quick fixes (`ruff check --fix`); different colors for errors and warnings; pylint/mypy checking as you type via a temporary copy. The Problems tab: sort by column, filter by file or tool, and notice files added or changed outside the IDE.
- These libraries would be IDE-only dependencies, like Pygments in the `ide` extra (`pip install -e ".[ide]"`), so programs never need them.

## Bigger features
- **Anchor follow-ups**: a visual anchor picker in the Properties panel (four edges to click, as in Visual Studio) instead of the dropdown; a form `minwidth`/`minheight` so anchored controls can't be squeezed together. ~~`dock`~~ Done (`layout.dock`, the `dock` property; edges are taken in the order controls were drawn, fill takes the rest). Dock follow-ups: a splitter between docked controls to drag their edge (WinForms' Splitter); dragging a docked control in the designer springs back (only its free edge resizes).
- **Make EXE follow-ups**: signing the program (Windows Authenticode, macOS codesign and notarizing; the certificate is per machine, in `.readymade/local.json`); a Mac app's bundle identifier; an installer (Inno Setup on Windows, a .dmg on the Mac); license notices for libraries that bundle other code of their own (today: each library's own license files).
- **More controls**: third-party controls from installed libraries appearing in the Toolbox (to decide: loading a library's controls from the project's environment into the IDE, with a labeled placeholder box when it can't load). VB's controls still missing, from Tk's own widgets:
  - ~~ProgressBar, Slider, UpDown, ScrollBar~~ Done (`controls/ranges.py`: ttk's Progressbar, Scale, Spinbox and Scrollbar, sharing `min`, `max`, `value` and a `change` event). Follow-ups: tick marks on a Slider (ttk's Scale has none; VB's TickFrequency); colors for the bars (Windows' and macOS's own themes ignore them, so not offered yet); a `scroll` event apart from `change` (VB's ScrollBar had both: while dragging, and after); decimal values (today whole numbers, as in VB).
  - ~~TabStrip, TreeView, ListView~~ Done (`controls/tabstrip.py`, `controls/trees.py`). A control on a TabStrip page keeps its `page` in the .form; the designer shows the page being worked on, apart from the starting `tab`. Follow-ups: access keys in tab captions (`&General`) and Ctrl+Tab between pages; pictures on TreeView nodes and ListView rows; ListView column widths saved from the designer, and its Icon and List views (Tk has neither); TreeView check boxes; editing a node's or row's text in place (VB's LabelEdit).
  - **StatusBar** and **Toolbar**: panels along the bottom (text, the time, Caps Lock), and rows of picture buttons. Their groundwork is done (`dock`, pictures on Buttons and Labels): today a docked Frame of picture Buttons and a docked Label do much of it.
  - **MaskedEdit**: as TextBox properties rather than a control (`mask = "(###) ###-####"`, numbers only), with Tk's validation.
  - **RichTextBox**: bold, colors and fonts in parts of the text (`tk.Text` tags); maybe a `rich` mode of TextBox. Loading and saving RTF probably isn't worth it.
  - **A data grid** (VB's MSFlexGrid): a table edited cell by cell, from a `ttk.Treeview` with an entry over the cell being edited, or a Canvas. Not named Grid (that's the layout container): Table, perhaps.
  - **DTPicker / MonthView**: Tk has no calendar, and tkcalendar is GPL (not one to bundle in EXEs), so our own drop-down month.
  - Not planned: DriveListBox, DirListBox, FileListBox (the file dialogs and a TreeView do better), Data, OLE, WebBrowser (Windows COM, or a browser engine), Winsock, Inet, MSComm, MMControl (Python's libraries do these: socket, urllib, pyserial; examples with `in_thread` instead), ImageList (pictures come from `images/`), Line and Shape as controls (a Tk widget can't be see-through; Canvas draws them).
- ~~**Control arrays**~~ Done: a control named `Digit[3]` is in the `Digit` array (`names.split_element`), `self.Digit[3]` in code, a `ControlArray` with `add()`, `remove()` and `del`; handlers are shared and told `index` first. In the designer, the `index` property starts one, and a pasted copy of one of its controls joins it. Follow-ups: menu item arrays (VB had them, for a recent-files list); `add()` for an array with no controls drawn.
- **Image drawing follow-ups**: flood fill (Pillow's `ImageDraw.floodfill`); mouse coordinates in the picture's pixels when it's scaled (stretch, zoom) or centered; anti-aliased shapes (Pillow draws them jagged; drawing larger and shrinking is the usual trick); undo for paint programs (keep copies of the picture).

## Biggest features
- **Grid follow-ups**: add and remove rows and columns from the designer (today: the Grid's `columns` and `rows` properties); show each track's size along the Grid's edges; a form that sizes itself to its contents; single-direction rows and columns (a `Stack`, like Qt's QHBoxLayout/QVBoxLayout), which would also cover Tk's pack.

There are two optional paths to this: One is keeping Tkinter for the IDE and designing a project with a different GUI backend, or having the IDE match the target project GUI.  Is a GUI target potentially a plugin?  Either way, this looks like a separation of concerns type of refactor.
  - Keep readymade's own API free of Tk: shapes are readymade objects, colors `#rrggbb`, angles in degrees, fonts `(family, size, style)`. Still Tk-specific: color names Canvas shapes accept beyond `#rrggbb`, and `.widget` / `form.root` (fine as documented escape hatches). If Qt: PySide6 (LGPL) rather than PyQt6 (GPL), for programs made with Make EXE.
- **Plugins**: A plugin architecture to extend features.  Allow other people to create plugins like VB or VS Code allows.
